## 2. 项目背景与要解决的问题

北京市的空气质量是公众长期关注的话题。环保部门在城区布设了多个监测站点，按小时记录 PM2.5、PM10、SO2、NO2、CO、O3 等污染物浓度，同时记录温度、气压、露点、降雨、风向、风速等气象条件。

这些数据单独看只是"一张很大的表"，要回答真实问题，需要一条完整的数据链路：

1. 数据本身可靠吗？缺多少、重复多少、有没有明显错误的数值？
2. 不同站点的污染水平有没有差别？差多少？
3. 污染物浓度在一天之内、一年之内怎么变化？
4. 这些结论怎么让不懂技术的人一眼看懂？

本项目要做的，就是把上面 4 个问题用**一条可验证、可复现的大数据处理流水线**回答出来，而不是用几张手工拼出来的图。

### 2.1 "大数据"在这里意味着什么（务实说明）

必须说清楚：42 万行、约 40MB 的 CSV，用 Excel 或 pandas 单机也能打开。本项目使用 Hadoop 生态，**不是为了性能，而是为了完整走通"存储—计算—服务—展示"的工程流程**，这是本专业的核心训练目标。

因此文档中不会声称"支撑海量数据""生产级高并发"。真实表述是：**在单机伪分布式环境下，完整实现了一套可扩展到集群的数据处理流程**。

## 3. 项目目标

### 3.1 总目标

构建一个从原始 CSV 到可视化大屏的完整系统：原始数据进入 HDFS，经 Spark SQL 清洗与聚合，结果由 Hive 管理并同步到应用库，Spring Boot 提供接口，Vue3 大屏展示，Matplotlib 输出独立分析图，全过程有文档、有日志、有可核对的数字。

### 3.2 可验证的分目标

| 编号 | 目标 | 验证方式 |
| --- | --- | --- |
| G1 | 原始数据完整入库，不被覆盖 | HDFS 上同时存在原始层与清洗层目录；原始文件只读 |
| G2 | 清洗过程可解释、可复现 | 清洗规则表 + 清洗前后记录数 + 缺失率报告，数字能对上 |
| G3 | 统计结果可追溯 | 任一大屏数字，都能用一条 Hive/Spark SQL 复算出来 |
| G4 | 前后端真实联调 | 大屏数据来自接口，接口数据来自数据库，断网改数据能反映到页面 |
| G5 | 图表口径一致 | Matplotlib 图与 Spark SQL 结果误差为 0（同一份 ADS 结果） |
| G6 | 工程可交付 | Git 提交历史、运行说明、测试记录齐全，他人按文档能跑起来 |

### 3.3 明确不做的事情（避免承诺过头）

- 不做实时监测（数据是 2013–2017 年的历史数据，页面必须标注"历史数据"）。
- 不做全国城市排名（数据集只有北京 12 个站点）。
- 不把污染物浓度当作 AQI 展示，也不自行判定"优良/轻度污染"等级（数据集无 AQI 字段，标准核验未完成）。
- 不做机器学习预测、爬虫、复杂权限系统。
- 不凭数据集里不存在的地理坐标画地图。

## 4. 建设范围

### 4.1 范围内（In Scope）

| 层次 | 内容 |
| --- | --- |
| 数据层 | UCI 原始 CSV 获取、校验、入库、清洗、分层存储（ODS / DWD / ADS） |
| 计算层 | Spark SQL 完成清洗、转换、分组聚合、时间维度分析 |
| 存储层 | HDFS 存文件，Hive 建表并管理元数据 |
| 服务层 | Spring Boot 三层架构，提供统计、查询、导出接口 |
| 展示层 | Vue3 + ECharts 大屏、数据管理页、查询页 |
| 分析层 | Python + Matplotlib 生成独立图表，并与 SQL 结果交叉核对 |
| 管理层 | Maven 父子工程、Git 版本控制、六类项目文档 |

### 4.2 范围外（Out of Scope，第一版）

实时流处理（Kafka/Flink）、集群高可用、容器化部署（Docker/K8s）、移动端、用户注册登录、模型训练、自动报告生成。

## 5. 技术选型与理由

| 技术 | 版本策略 | 在本项目中的实际作用 | 为什么选它 |
| --- | --- | --- | --- |
| Hadoop (HDFS) | 3.3.x（待阶段二在虚拟机内核实） | 存放原始 CSV、清洗后 Parquet、分析结果 | 课程核心技术；提供"数据湖"式分层存储 |
| Hive | 3.1.x | 建库建表、管理元数据、SQL 查询 | 让文件拥有"表结构"，便于 SQL 分析与对外解释 |
| Spark SQL | 3.5.x（PySpark 3.5.3 已就位） | 清洗、转换、聚合、写回结果 | 计算引擎；同一份 SQL 既能跑清洗也能跑统计 |
| Maven | 3.6.3（已装，建议升 3.9.x） | 依赖管理、父子工程构建 | 课程要求；多模块工程的标准做法 |
| Spring Boot | 2.7.18（首选，配 JDK 8） | 后端 REST 接口 | 与已装 JDK 8、课程教程一致，Hive JDBC 客户端在 Java 8 下最稳 |
| MyBatis-Plus | 3.5.x | 数据访问层 | 少写样板 SQL，仍保留手写 SQL 能力 |
| Vue 3 | 3.5.x + Vite | 前端页面与大屏 | 课程要求；组合式 API 上手快 |
| ECharts | 5.5.x | 柱状图、折线图、热力图 | 国内文档全、示例多、支持大屏自适应 |
| Element Plus | 2.x | 表格、表单、分页、日期选择 | 减少手写 UI，专注数据逻辑 |
| Python + Matplotlib | 3.13 / 3.10.6（已装） | 独立分析图表 | 课程要求；出图快，便于写进论文 |
| Git | 2.55.0（已装） | 版本控制 | 课程要求；保留开发过程证据 |

### 5.1 关于"为什么后端不直接用 JDK 21"

本机同时装了 JDK 8 和 GraalVM JDK 21。后端选 JDK 8 + Spring Boot 2.7 的理由是**降低风险**，不是"技术落后"：

- Hive 3.1.3 的 JDBC 客户端在 Java 8 下最成熟，换成 Java 21 可能出现模块化反射告警甚至失败。
- 已安装的 Maven 3.6.3 与 JDK 8 是匹配组合，无需改环境。
- 课程教程的 Spring Boot 示例多为 2.x，跟着做阻力最小。

代价是 Spring Boot 2.7 已停止官方维护（2023-11 之后不再发版）。对不联网的课程项目，这个代价可以接受。若你希望使用新技术栈，备选方案是 Spring Boot 3.3 + JDK 21 + Maven 3.9，详见 05 文档第 6 节。

## 6. 数据使用与合规

1. **来源唯一**：只使用 UCI 官方数据集，不使用来源不明的"整理版""清洗版"CSV。
2. **许可与引用**：下载时记录官网标注的许可协议与推荐引用格式，写入 README 与论文"数据来源"一节。
3. **字段属性区分**：原始字段、规范化字段、衍生字段在数据字典中分别列示，衍生字段一律写明计算公式。
4. **不虚构**：所有统计数字必须由代码产出；文档中的示例数字必须标注"示例，待实测回填"。
5. **不冒充**：不把浓度当 AQI；不把历史数据叫"实时"；不把 12 个站点包装成"全国排名"。
6. **可追溯**：每张图、每个接口都注明数据来自哪张表、哪条 SQL。

## 9. 成功标准（项目级）

1. 评审者按《运行说明》从零启动，能在 30 分钟内看到大屏出数。
2. 大屏上任意一个数字，能在 2 分钟内用一条 SQL 复算并得到相同结果。
3. 清洗前后记录数、缺失率、异常值数量三者之和关系能自洽解释。
4. 代码可编译、可运行，无写死的假数据分支。
5. 文档与实现一致：文档里写的表名、字段名、接口路径，代码中真实存在。
